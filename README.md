# Customer Payments & Collection Intelligence

A portfolio project for practicing SQL Server, Python/Pandas, data quality, ETL, statistics, business KPIs, and later Power BI/Excel reporting.

> **Data notice:** All records are synthetic and generated for learning. They do not represent a real company or real customers. Do not describe the project as having achieved business improvements until analysis has been completed and evidence supports the claim.

## Business question

A fictional B2B company wants to understand invoice payment behavior and overdue receivables. The analyst should validate source data, build reproducible tables, calculate well-defined KPIs, investigate patterns, and communicate limitations and recommendations.

## Project phases

1. **Phase 1 — Data design and generation (current):** generate deterministic synthetic customers, invoices, and payment transactions; inspect quality; understand the data dictionary.
2. Phase 2 — Load the clean tables into SQL Server and practice SQL analysis.
3. Phase 3 — Build a repeatable Python/Pandas ETL and exploratory analysis workflow.
4. Phase 4 — Create Power BI dashboard and Excel reconciliation workbook when those tools are available.
5. Phase 5 — Write a findings report based on actual calculations, then update the CV with verified outcomes.

## Data model

- `customers.csv`: one row per customer (`customer_id` is intended unique).
- `invoices.csv`: one row per invoice (`invoice_id` is intended unique). An invoice belongs to one customer.
- `payments.csv`: one row per payment transaction. Multiple payments may apply to one invoice; `payment_id` is intended unique.
- `data_quality_issues.csv`: synthetic issue register describing deliberately inserted raw-data problems. This is a teaching aid; validate the records yourself rather than blindly relying on the register.

Relationships:
- `customers.customer_id` 1 → many `invoices.customer_id`
- `invoices.invoice_id` 1 → many `payments.invoice_id`

The raw files intentionally contain a small number of controlled data-quality issues (for example, a duplicate customer row, a missing customer segment, a malformed region value, an invalid invoice amount, and a payment referencing a nonexistent invoice). Some are designed to be detected, documented, and resolved in later phases. Do not silently delete or change records: record each decision and explain its impact.

## Setup (beginner-friendly)

Use Python 3.10+.

### 1. Open a terminal in this project folder

```bash
cd New-Skills/customer-payments-analytics
```

### 2. Create a virtual environment

Windows PowerShell:
```powershell
py -m venv .venv
.venv\\Scripts\\Activate.ps1
```

macOS/Linux:
```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Install dependencies

```bash
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 4. Generate the synthetic raw data

```bash
python src/generate_data.py
```

This writes CSVs to `data/raw/`. Generation is deterministic with a fixed seed, so the same input configuration produces reproducible data.

### 5. Inspect the files

Open the CSVs in a text editor or load them in Python. Excel is not required. To inspect the first few rows:

```bash
python -c "import pandas as pd; print(pd.read_csv('data/raw/customers.csv').head())"
```

### 6. Run the starter cleaner

```bash
python src/clean_data.py
```

This creates initial processed copies and a quality report in `data/processed/`. It applies only documented, conservative transformations. Review the report and source code before treating processed data as analysis-ready.

### 7. Run tests

```bash
python -m unittest discover -s tests -v
```

- **Power BI alternative for now:** produce charts with Matplotlib and document the dashboard design. When Power BI Desktop becomes available, import the processed CSVs and follow `powerbi/README.md`.

## KPI definitions (initial proposals — confirm with business rules)

- **Invoiced amount:** sum of valid invoice amounts, excluding cancelled invoices if the business defines cancellations that way.
- **Amount paid:** sum of valid payment transactions. Avoid counting payments twice after joins.
- **Outstanding balance:** invoice amount minus allocated payments, floored at zero only if overpayments are handled separately and documented.
- **Overdue invoice:** unpaid balance > 0 and due date earlier than the chosen reporting date.
- **Overdue balance:** outstanding balance of overdue invoices.
- **Collection rate:** define the denominator and time window explicitly. A simple paid/invoiced ratio for a cohort is not interchangeable with cash collected during a calendar month.
- **Days sales outstanding (DSO):** requires a defined revenue basis and period; do not compute it from this synthetic invoice table without stating the chosen approximation and its limitations.
